    Building and cleaning up:
        1. One build directory per project: where the user or the project already puts it (a CARGO_TARGET_DIR they set, a build cache on another disk, a shared virtualenv they named), else inside the project: Rust's target/ at the workspace root, build/ for C and C++, the project's own virtualenv. Never make a second one: no CARGO_TARGET_DIR or --target-dir of your own, no scratch crate with its own [workspace]. A second cache rebuilds every dependency into new gigabytes; code that needs the project's crate goes in the workspace as a member or an example.
        2. Build the same way every time: the workspace build, the same features and profile, niced and with a job cap so the machine stays usable. A build that recompiles dependencies means something changed in how you build; stop and find it. No release or full test builds unless asked.
        3. Don't wipe the build cache to make room (cargo clean, rm -rf target): the next build costs minutes. Remove what is stale instead. Build tools keep every old copy when dependencies or features change; for Rust, `cargo build --message-format=json` (a no-op when nothing changed) lists the files the current build uses, and the rest of target/*/deps, old target/*/incremental dirs and binaries no build makes anymore can go.
        4. Before anything that needs gigabytes (a release or LTO build, a toolchain, a model or dataset download), check free disk. When it's low, tell the user before filling it.
        5. Temporary files go in one gitignored scratch directory per task inside the project, never /tmp. Delete it before you finish, or say what you kept and why.
        6. Stop what you started before you finish: servers, watchers, mocks, background builds. Find them by exact name or by working directory; pgrep -f and pkill -f also match your own shell's command line.
        7. No unnecessary timeouts. A long command goes to the background: piccosta moves a command there when it runs long and sends you its result as a message when it ends. Don't wait on it in the foreground, don't sleep or poll for it, and don't give a command a long timeout to watch it; keep working, or end your turn.
    Code style, my default (from my C; carried over to other languages):
        1. Comments narrate the reasoning: plain, conversational comments that walk the next reader through what a block does and why. All cases it handles, what it assumes, the reason for an odd step. One comment per logical step, above the step. No diff commentary ("changed X to Y"), no filler ("robust", "comprehensive", "seamless").
        2. Function headers say what it does, then input, output, and decisions.
        3. Names say what the thing is: full words, no abbreviations a reader has to decode. Single letters only for a loop index.
        4. No magic numbers: named constants with a comment saying where the value came from.
        5. Formatting comes from the language formatter.
    What has worked in my own sessions:
        1. Answer the question that was asked. Do not drift into a grander one.
        2. Verify by running the real thing. Before reporting any benchmark or experiment number, confirm with a small tracer that the pipeline under test is actually connected end to end.
        3. Report outcomes faithfully: failing output verbatim, if things are broken or skipped. Report every metric and call out any metric that moved against it.
        4. Nothing hardcoded: no paths, hosts, ports, usernames, URLs or model names in code; they come from config or the environment with a documented default.
        5. Discuss before acting.
        6. Watch for a past decision or bug that lingers. Bugs hide inside true stories: a result that looks like the negative you expected. When a run works but the number does not move, stop, say the design in one sentence, and measure the simplest thing it implies.
        7. Delete what you create temporarily before you finish. Failed approaches get a short note saying what was tried, why it failed, and what would need to change.
        8. Do not deal in absolute decisions.
        9. Don't block on asking whether to commit. Commit finished, checked work as you go and say so; pushing stays the user's call.
